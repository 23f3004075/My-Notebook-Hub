1 RAG System Design — Production Architecture

Interviewers no longer ask “what is RAG?” They ask you to design a RAG system that survives real traffic, bad retrievals, and LLM provider outages. Start with the end‑to‑end flow, then defend every component.

▶
Walk me through the architecture of a production RAG system.
RAG System Design

A production RAG system has two planes: the offline ingestion plane and the online serving plane. Most candidates only describe the happy path; strong candidates describe the boundaries and failure modes.

Production RAG — end-to-end data flow ┌──────────────────────────────────────────────────────────────────────────────┐ │ OFFLINE INGESTION │ │ │ │ Source docs ──► Parser ──► Chunker ──► Embedding model ──► Vector DB │ │ (PDF/HTML/DB) (layout, (semantic, (batch, async) (HNSW / IVF) │ │ tables) parent-child) │ │ │ │ │ └──► Metadata store (Postgres) │ │ (source, version, ACLs) │ └──────────────────────────────────────────────────────────────────────────────┘ ┌──────────────────────────────────────────────────────────────────────────────┐ │ ONLINE SERVING │ │ │ │ User query ──► API gateway ──► Query rewrite ──► Retrieval │ │ (FastAPI) (HyDE / multi-query) │ │ │ │ │ ┌─────────────────┴─────────────────┐ │ │ ▼ ▼ │ │ Dense search Sparse BM25 │ │ (vector DB) (keyword index) │ │ └─────────────┬───────────────────┘ │ │ ▼ │ │ Fusion (RRF) │ │ ▼ │ │ Cross-encoder reranker │ │ ▼ │ │ Top-k chunks + citations │ │ ▼ │ │ Prompt assembly (context window budget) │ │ ▼ │ │ LLM provider (streaming SSE) │ │ ▼ │ │ Response + source attribution │ └──────────────────────────────────────────────────────────────────────────────┘
They want to see that you separate ingestion from serving, that you can name the retrieval stages, and that you know where latency and cost are introduced.

Key components to defend:

  • Chunking strategy — fixed-size vs semantic vs parent-child. Parent-child retrieval preserves context: embed small chunks for search, return the larger parent chunk to the LLM.
  • Embedding model — dimension, max sequence length, domain fit. Production embedding calls are batched and async.
  • Vector index — HNSW for low-latency recall, IVF-PQ when memory is constrained. Know the recall–latency–memory trade-off.
  • Hybrid retrieval — dense vectors miss exact keyword matches; BM25 misses paraphrases. Fuse with Reciprocal Rank Fusion (RRF).
  • Reranker — a cross-encoder re-scores the top 20–50 candidates and usually gives the single largest precision gain.
  • Prompt assembly — enforce a token budget; put the most relevant chunks first and last (“lost in the middle” mitigation).
Whiteboard the two planes separately. Draw ingestion left-to-right, serving top-to-bottom. Explicitly call out where you would add caching, rate limiting, and observability. Mention the metadata store — ACL filtering is a production requirement, not an afterthought.
▶
How do you choose a chunking strategy? What breaks if you get it wrong?
RAG

Chunking is the highest-leverage decision in RAG because retrieval can only return what exists in a chunk. Three dominant strategies:

StrategyHow it worksBest forFailure mode
Fixed-size Split every N tokens with overlap. Homogeneous text, quick baseline. Cuts sentences/tables mid-thought; retrieval returns incomplete context.
Semantic Split on topic boundaries using embedding similarity. Long documents with clear sections. Variable chunk sizes; small chunks may lack context.
Parent-child Embed small child chunks; return the larger parent chunk to the LLM. Q&A over manuals, policies, code docs. Requires a two-level store; parent retrieval can blow the token budget.
If chunks are too small, the LLM receives fragments and hallucinates to fill gaps. If chunks are too large, retrieval precision drops and you waste context tokens. Always evaluate chunk size empirically — do not guess. 
python · semantic chunking sketch
from langchain_experimental.text_splitter import SemanticChunker
from langchain_openai import OpenAIEmbeddings

splitter = SemanticChunker(
    OpenAIEmbeddings(model="text-embedding-3-small"),
    breakpoint_threshold_type="percentile",
    breakpoint_threshold_amount=95,
)
chunks = splitter.split_text(document)
# Each chunk is a semantically coherent unit, not an arbitrary token window.
Say: “I start with 400–600 token chunks with 10–15% overlap, measure retrieval recall@k and answer faithfulness, then try semantic or parent-child if the baseline fails.” That shows empirical discipline.

Implement hybrid search combining dense vectors and BM25. How do you fuse the scores?
RAG Python

Dense retrieval captures semantic similarity; BM25 captures exact term overlap. In production, you run both, then fuse the ranked lists. Reciprocal Rank Fusion (RRF) is the standard because it is score-scale invariant. 

python · hybrid retrieval with RRF and cross-encoder rerank
from typing import List, Dict
import numpy as np

def reciprocal_rank_fusion(
    ranked_lists: List[List[str]],
    k: int = 60,
) -> List[tuple[str, float]]:
    """
    RRF: score(d) = Σ 1 / (k + rank_i(d))
    k dampens the influence of high ranks; 60 is the common default.
    """
    scores: Dict[str, float] = {}
    for ranked in ranked_lists:
        for rank, doc_id in enumerate(ranked):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)


def hybrid_retrieve(query: str, top_k: int = 50) -> List[str]:
    dense_ids = vector_store.search(query_embedding(query), top_k=top_k)
    sparse_ids = bm25_index.search(query, top_k=top_k)

    fused = reciprocal_rank_fusion([dense_ids, sparse_ids])
    candidate_ids = [doc_id for doc_id, _ in fused[:top_k]]

    # Cross-encoder rerank: expensive but highest precision gain
    pairs = [(query, doc_store[d].text) for d in candidate_ids]
    rerank_scores = cross_encoder.predict(pairs)
    reranked = sorted(
        zip(candidate_ids, rerank_scores),
        key=lambda x: x[1],
        reverse=True,
    )
    return [doc_id for doc_id, _ in reranked[:10]]
They want to see that you know RRF is scale-free and that reranking is a separate, more expensive stage. Mentioning “hybrid + rerank” without explaining the fusion function is a partial answer.
In the interview, draw the two parallel retrieval branches, the fusion box, and the reranker. Say: “BM25 handles product codes and names; dense handles paraphrases. RRF combines them without normalizing incompatible score distributions.”

How do you evaluate a RAG system? Explain faithfulness vs answer relevance.
RAG Evaluation

RAG evaluation must cover retrieval quality and generation quality separately. The RAGAS framework is the common vocabulary.

MetricQuestion it answersWhat failure it catches
Context precision Are the retrieved chunks actually relevant? Noisy retrieval; vector index drift.
Context recall Did we retrieve all the evidence needed? Missing evidence → hallucination.
Faithfulness Is every claim in the answer supported by the retrieved context? Hallucination, unsupported extrapolation.
Answer relevance Does the answer actually address the question? Evasive, off-topic, or overly generic answers.

Strong candidates distinguish “the answer is wrong” from “the retrieval was wrong.” If context recall is low, no prompt engineering will fix the answer.
Say: “I maintain a golden set of 100–300 question–answer–context triples. I run RAGAS on every retrieval or prompt change and block deploys if faithfulness drops more than 3 points.”

What are the most common production RAG failure modes and how do you detect them?
RAG Production
  • Lost in the middle — the LLM ignores chunks in the middle of a long context. Detect by placing the gold chunk at different positions and measuring answer accuracy. Mitigate by reordering: most relevant first and last.
  • Retrieval drift — embeddings or index parameters change silently. Detect with context precision and recall on a fixed golden set after every deploy.
  • Chunk boundary truncation — the answer spans two chunks but neither is retrieved. Detect with context recall; mitigate with parent-child retrieval or larger overlap.
  • Prompt injection via retrieved content — malicious documents instruct the LLM to ignore system prompts. Detect with input sanitization and output policy checks; never trust retrieved text as instructions.
  • Stale index — documents updated but embeddings not re-indexed. Detect with source-version metadata and freshness audits.
A RAG system can fail silently: the answer looks fluent but is unsupported. Log every retrieval’s document IDs and scores, and sample production traces for human review weekly.
In the interview, say: “I instrument retrieval separately from generation. When a bad answer appears, I first check whether the correct chunk was retrieved (context recall). If it was, the problem is generation; if not, the problem is retrieval.”

2 FastAPI for AI Backends — Async, Streaming, and Resilience

FastAPI is the default AI backend because it is async-first, has native streaming, and integrates Pydantic validation. Interviewers probe the internals: the event loop, blocking calls, and what happens when an LLM provider stalls.

▶
Why is FastAPI the modern default for AI backends? Explain async vs sync with concrete numbers.
FastAPI Python

LLM calls are I/O-bound: the CPU is idle while waiting for the network. A synchronous worker is blocked for the entire 3–10 second LLM call. An async worker can serve hundreds of concurrent requests while waiting.

Sync vs async concurrency under 5-second LLM latency SYNC (Flask, 4 workers): Request 1 ──████████████████████ 5s Request 2 ── queued ───────────── 10s Request 3 ── queued ───────────── 15s Request 4 ── queued ───────────── 20s Throughput: 4 requests per 5s → 0.8 req/s ASYNC (FastAPI, 4 workers, all awaiting): Request 1 ──████████████████████ 5s Request 2 ──████████████████████ 5s Request 3 ──████████████████████ 5s Request 4 ──████████████████████ 5s Throughput: 4 requests per 5s, but the event loop can interleave hundreds of pending coroutines → effectively 400+ concurrent in-flight.

Four reasons FastAPI wins for AI:

  1. Async-first design — async def endpoints let one worker handle many in-flight LLM calls. Flask/Django are synchronous by default; each request blocks a worker.
  2. Native streaming — StreamingResponse and SSE support token-by-token LLM output out of the box. Flask requires manual chunked encoding.
  3. Pydantic integration — request/response schemas are validated before your code runs. Critical when passing structured prompts and tool calls.
  4. Type hints as contracts — the function signature is the API schema. Refactoring is safe and auto-generated OpenAPI docs stay accurate.
Async is not automatically faster. If you call a synchronous database driver or a blocking library inside an async def endpoint, you block the event loop and destroy concurrency. Use asyncpg, httpx.AsyncClient, and async SDKs.
The killer follow-up: “You used FastAPI with sync SQLAlchemy. What happens?” Answer: the sync call blocks the event loop, so the app behaves like a synchronous service — worse than Flask because you paid the async complexity cost for nothing.
Say: “I treat async def as a promise that every downstream I/O is non-blocking. For CPU-bound work — local embedding, reranking — I offload to a thread pool or a separate worker, never the event loop.”
▶
Implement a streaming RAG endpoint with Server-Sent Events (SSE).
FastAPI RAG

Streaming is non-negotiable for user-facing LLM products: time-to-first-token dominates perceived latency. The endpoint retrieves context, assembles the prompt, then streams the LLM output token by token as SSE events. 

python · FastAPI SSE streaming RAG endpoint
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
import asyncio, json

app = FastAPI()

class RAGRequest(BaseModel):
    question: str
    top_k: int = 5
    tenant_id: str

async def rag_stream(req: RAGRequest):
    # 1. Retrieval (async)
    chunks = await retriever.retrieve(req.question, top_k=req.top_k)
    context = "\n\n".join(c.text for c in chunks)

    # 2. Prompt assembly with explicit token budget
    prompt = build_prompt(
        system="Answer only from the context. Cite chunk IDs.",
        context=context,
        question=req.question,
    )

    # 3. Stream LLM tokens
    async for token in llm.stream(prompt, tenant_id=req.tenant_id):
        yield f"data: {json.dumps({'token': token})}\n\n"

    # 4. Emit citations as a final event
    citations = [{"id": c.id, "source": c.source} for c in chunks]
    yield f"data: {json.dumps({'citations': citations})}\n\n"
    yield "data: [DONE]\n\n"

@app.post("/v1/rag/stream")
async def rag_endpoint(req: RAGRequest):
    return StreamingResponse(
        rag_stream(req),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",  # disable nginx buffering
        },
    )
They want to see: async generator, SSE framing (data: …\n\n), disabling proxy buffering, and a final citations event. Mentioning X-Accel-Buffering: no signals real deployment experience.
If asked to extend: add a heartbeat comment (: ping\n\n) every 15 seconds to keep proxies from closing idle connections. Add backpressure: if the client disconnects, cancel the upstream LLM stream.

How does Pydantic protect an AI backend? Give a production example.
FastAPI

Pydantic validates and coerces request data before your handler runs. In AI systems this prevents malformed prompts, oversized payloads, and invalid tool-call schemas from reaching expensive downstream services. 

python · Pydantic model with production constraints
from pydantic import BaseModel, Field, field_validator

class RAGQuery(BaseModel):
    question: str = Field(..., min_length=3, max_length=2000)
    top_k: int = Field(default=5, ge=1, le=20)
    temperature: float = Field(default=0.0, ge=0.0, le=1.0)
    tenant_id: str = Field(..., pattern=r"^[a-z0-9-]{3,32}$")

    @field_validator("question")
    @classmethod
    def reject_prompt_injection_markers(cls, v: str) -> str:
        forbidden = ["ignore previous instructions", "system prompt"]
        lower = v.lower()
        if any(marker in lower for marker in forbidden):
            raise ValueError("Potential prompt injection detected")
        return v.strip()

# FastAPI automatically returns 422 with a detailed error body
# before your retrieval or LLM code executes.
They want to hear that validation is a cost control and a safety layer, not just developer convenience. A rejected request costs 0 tokens; a malformed request that reaches the LLM costs money and may leak data.
Say: “I put hard limits on top_k, question length, and temperature at the schema layer. I also validate tenant IDs against an allow-list before any retrieval to prevent cross-tenant data leakage.”

Design rate limiting and a circuit breaker for an LLM-backed FastAPI service.
FastAPI Resilience

LLM calls are slow, expensive, and can fail in bursts. You need two protections: rate limiting to control cost and fairness, and a circuit breaker to stop hammering a failing provider.

Circuit breaker state machine ┌─────────────┐ │ CLOSED │ normal operation; requests pass through │ (healthy) │ └──────┬──────┘ │ failure threshold exceeded ▼ ┌─────────────┐ │ OPEN │ fail fast; requests return cached/fallback │ (tripped) │ └──────┬──────┘ │ recovery timeout elapses ▼ ┌─────────────┐ │ HALF-OPEN │ allow a probe request │ (testing) │ └──────┬──────┘ │ │ success failure │ │ ▼ ▼ CLOSED OPEN 
python · simple async circuit breaker
import asyncio, time
from enum import Enum

class State(Enum):
    CLOSED = "closed"
    OPEN = "open"
    HALF_OPEN = "half_open"

class CircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=30.0):
        self.state = State.CLOSED
        self.failures = 0
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.last_failure_time = 0.0
        self._lock = asyncio.Lock()

    async def call(self, fn, *args, **kwargs):
        async with self._lock:
            if self.state == State.OPEN:
                if time.time() - self.last_failure_time > self.recovery_timeout:
                    self.state = State.HALF_OPEN
                else:
                    raise RuntimeError("Circuit open: failing fast")
        try:
            result = await fn(*args, **kwargs)
            async with self._lock:
                if self.state == State.HALF_OPEN:
                    self.state = State.CLOSED
                self.failures = 0
            return result
        except Exception:
            async with self._lock:
                self.failures += 1
                self.last_failure_time = time.time()
                if self.failures >= self.failure_threshold:
                    self.state = State.OPEN
            raise
Rate limiting per IP is insufficient for LLM services. Limit per tenant and per model, and make the limit cost-aware: a request for a 4k-token completion costs far more than a 100-token classification.
In the interview, layer the protections:
  1. API key authentication → tenant identity.
  2. Sliding-window or token-bucket rate limiter per tenant.
  3. Circuit breaker around each LLM provider adapter.
  4. Fallback chain: primary → secondary provider → cached response → graceful error.

Write a production Dockerfile for a FastAPI AI service. Why multi-stage?
FastAPI Deployment

Multi-stage builds separate the build toolchain from the runtime image. The result is a smaller, faster-to-pull, lower-CVE image — critical for autoscaling and cold starts.

3 Out-of-Distribution (OOD) Detection for Production ML

OOD questions test whether you understand that a model is only valid on the distribution it was trained on. In production, inputs drift, adversaries probe, and user behaviour changes. You need to detect this before the model confidently outputs nonsense.

▶
What is OOD detection and why does it matter for an AI Engineer?
OOD Production

OOD detection is the process of flagging inputs that fall outside the training distribution. A classifier trained on cat/dog images may confidently label a medical X-ray as “dog” because it has never seen an X-ray and has no concept of “unknown.”

For AI Engineers, OOD matters in three places:

  • Safety — reject inputs the model cannot handle instead of returning a hallucinated answer.
  • Monitoring — track OOD rate as an early warning of data drift or distribution shift.
  • Routing — route OOD inputs to a human review queue or a fallback model instead of the primary model.
They want to hear that OOD detection is not just a research metric — it is a production control that gates model predictions.
Frame OOD as part of the inference contract: “If the input is OOD, the model must abstain, not guess. Abstention is a feature.”
▶
Compare OOD detection methods: statistical range checks, Mahalanobis distance, and energy-based scores.
OOD
MethodHow it worksProsConsUse when
Range / statistical Flag if a feature exceeds training min/max plus a margin. Trivial, interpretable, zero training cost. Misses multivariate OOD; ignores correlations. Tabular features with clear bounds; first-line guardrail.
Mahalanobis distance Distance to the training mean in covariance-normalized feature space. Captures correlations; works on embeddings. Assumes Gaussian-ish distribution; covariance inversion is costly at high dim. Embedding-space OOD; penultimate-layer features.
Energy-based Use the model’s logits: -T·logsumexp(logits/T). No extra training; theoretically grounded. Requires logits; threshold is model-specific. Neural classifiers where logits are available.
Range checks are necessary but not sufficient. A tabular input can be within each individual feature’s range but still be an impossible combination (e.g., age=5 and income=$500k). Mahalanobis catches this; univariate range checks do not.
In the interview, propose a two-tier system: cheap range checks at the API boundary, then Mahalanobis or energy-based scoring on the model’s internal representation before the prediction is returned.
▶
Implement Mahalanobis-distance OOD detection for embeddings.
OOD Python

Mahalanobis distance measures how many standard deviations an embedding is from the training distribution, accounting for feature correlations. Calibrate the mean and covariance on in-distribution reference data, then set a threshold at a high percentile (e.g., 99th). 

python · Mahalanobis OOD detector
import numpy as np

class MahalanobisOOD:
    def __init__(self, reg: float = 1e-5):
        self.mean = None
        self.inv_cov = None
        self.threshold = None
        self.reg = reg  # regularization for numerical stability

    def fit(self, embeddings: np.ndarray, percentile: float = 99.0):
        """embeddings: (n_samples, n_features) in-distribution reference."""
        self.mean = embeddings.mean(axis=0)
        cov = np.cov(embeddings, rowvar=False)
        cov += self.reg * np.eye(cov.shape[0])
        self.inv_cov = np.linalg.inv(cov)

        distances = self.score(embeddings)
        self.threshold = np.percentile(distances, percentile)
        return self

    def score(self, embeddings: np.ndarray) -> np.ndarray:
        diff = embeddings - self.mean
        # (x - μ)ᵀ Σ⁻¹ (x - μ)
        left = diff @ self.inv_cov
        return np.sqrt(np.sum(left * diff, axis=1))

    def is_ood(self, embedding: np.ndarray) -> bool:
        return float(self.score(embedding.reshape(1, -1))[0]) > self.threshold

# Calibration
detector = MahalanobisOOD().fit(train_embeddings, percentile=99.0)

# Inference gate
if detector.is_ood(new_embedding):
    return {"status": "abstain", "reason": "out_of_distribution"}
return model.predict(new_embedding)
Mention that you calibrate the threshold on a held-out in-distribution set and validate it on a known OOD set. Without a threshold calibration story, the code is incomplete.
If the interviewer asks “what about high-dimensional embeddings?” — say you optionally apply PCA or use a shrinkage covariance estimator, because the full covariance matrix becomes unstable when dimensions exceed samples.
▶
How do you integrate OOD detection into a FastAPI inference service without adding unacceptable latency?
OOD FastAPI

OOD detection must be cheap enough to run on every request. The pattern is: cheap range checks first, then Mahalanobis on a low-dimensional projection, then the model. 

python · FastAPI inference gate with OOD checks
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
import numpy as np

app = FastAPI()
range_monitor = DataDriftMonitor(margin=0.1)
range_monitor.fit(training_feature_ranges)
mahalanobis = MahalanobisOOD().fit(train_embeddings, percentile=99.0)

class PredictRequest(BaseModel):
    features: dict[str, float]
    text: str

@app.post("/predict")
async def predict(req: PredictRequest):
    # Tier 1: univariate range check (microseconds)
    drift = range_monitor.check(req.features)
    if not drift["in_distribution"]:
        raise HTTPException(
            status_code=422,
            detail={"error": "ood_input", "warnings": drift["warnings"]},
        )

    # Tier 2: embedding-space Mahalanobis check
    embedding = embedder.encode(req.text)
    if mahalanobis.is_ood(embedding):
        return {"prediction": None, "status": "abstain", "reason": "ood_embedding"}

    # Tier 3: model prediction
    return {"prediction": model.predict(req.features, embedding)}
The two-tier design shows latency awareness: the cheap check catches obvious garbage before you pay for embedding and covariance math.
Say: “I run the range check before embedding, and the Mahalanobis check on a 16–64 dimensional PCA projection. That keeps the OOD gate under 5 ms on CPU.”

4 System Engineering — LLM Gateway, Cost, Latency, and Caching

The highest-weight round in 2026 AI Engineer loops is the production system design round. You must design the infrastructure around the model: routing, fallback, cost tracking, caching, and multi-tenant fairness.

▶
Design an LLM Gateway that sits between your apps and multiple providers.
System Design Production

An LLM Gateway centralizes authentication, routing, rate limiting, caching, fallback, and observability. It prevents every team from re-implementing provider-specific retry logic and cost tracking.

Key design decisions:

  • Request Router — classify query complexity; route simple requests to a cheap/fast model and complex ones to a frontier model. Respect per-tenant budgets.
  • Semantic Cache — exact hash match first (Redis O(1)), then vector similarity. Include model, temperature, and system-prompt hash in the cache key.
  • Provider Adapter Layer — normalize provider APIs, retries with exponential backoff, failover chain (OpenAI → Anthropic → local vLLM).
  • Observability — log input/output tokens, model, latency, cost, tenant, cache hit/miss for every request.
The gateway is stateless, so it scales horizontally. Cache and rate-limit counters are shared (Redis cluster). Streaming responses bypass the cache but are still logged for analytics.
Whiteboard the gateway as a layered box. Then deep-dive into one layer the interviewer chooses — usually routing or caching. Have numbers ready: “20–40% cache hit rate is typical for factual Q&A.”
▶
Estimate the LLM cost of a multi-step agent session. What dominates and how do you reduce it?
System Design Cost

In a multi-step agent, every step re-sends the full conversation history plus tool schemas. Input token cost compounds with each step; output tokens are usually smaller but priced higher. 

text · cost formula
cost_per_session = Σ over steps [
    (system_prompt_tokens
     + history_tokens_at_step_i
     + tool_schema_tokens
     + new_input_tokens) × input_price
    + output_tokens_at_step_i × output_price
]

Example: a 4-step support agent with a mid-tier model at $1/M input and $3/M output costs roughly $0.01 per session. At 100k sessions/day that is $1,000/day ≈ $30k/month just in LLM API costs.

Senior interviewers expect back-of-the-envelope arithmetic. Practise saying the formula out loud and plugging in numbers.

Cost reduction levers:

  • Truncate or summarize history — long sessions cost disproportionately more because input tokens compound.
  • Model tiering — route 40% of traffic to a model that is 1/10 the cost → ~36% total cost reduction.
  • Semantic cache — 20–40% hit rate directly removes LLM calls.
  • Shorter prompts — every 1k tokens of system prompt removed saves money on every request.
  • Batch API where available — asynchronous batch inference is often 50% cheaper for non-latency-sensitive work.
If asked “how would you cut cost by 40%?” — say: “I would first instrument cost per tenant and per route. Then tier models, add semantic caching for repeated queries, and truncate history with a rolling summary. I would A/B test quality after each change.”

Design a semantic cache for LLM responses. What goes into the cache key?
System Design Caching

A semantic cache returns a previously generated answer when a new query is semantically similar to an old one, not just textually identical. It has two tiers: exact hash match and vector similarity. 

python · Redis + vector semantic cache sketch
import hashlib
from redisvl.extensions.cache.llm import SemanticCache
from redisvl.utils.vectorize import OpenAITextVectorizer

cache = SemanticCache(
    name="llm_cache",
    redis_url="redis://localhost:6379",
    vectorizer=OpenAITextVectorizer(model="text-embedding-3-small"),
    distance_threshold=0.15,  # similarity threshold
    ttl=3600,                 # 1 hour for factual Q&A
)

def make_cache_key(tenant_id: str, model: str, temperature: float, system_prompt: str):
    system_hash = hashlib.sha256(system_prompt.encode()).hexdigest()[:16]
    return f"{tenant_id}:{model}:{temperature}:{system_hash}"

async def cached_completion(tenant_id, model, temperature, system_prompt, query):
    key = make_cache_key(tenant_id, model, temperature, system_prompt)
    cached = cache.check(prompt=query, cache_key=key)
    if cached:
        return cached[0]["response"]  # cache HIT

    response = await llm.complete(
        model=model,
        temperature=temperature,
        system=system_prompt,
        prompt=query,
    )
    cache.store(prompt=query, response=response, cache_key=key)
    return response
Do not cache across tenants unless the data is provably non-sensitive. Cache keys must include tenant identity. Caching a response generated with one tenant’s retrieved context for another tenant is a data leak.
They want to hear: two-tier cache, model/temperature/system-prompt in the key, TTL by query type, and tenant isolation.
Say: “Exact match first because it is O(1) and free. Then vector similarity with a tight threshold — 0.12–0.18 cosine distance for factual Q&A. Creative tasks get a much tighter or disabled semantic cache.”

When does model tiering make economic sense? When is it a mistake?
System Design Cost

Model tiering matches model capability to task complexity. A small model classifies intent; a mid-tier model handles standard Q&A; a frontier model handles multi-step reasoning or code generation.

TierUse caseCost vs frontier
Routing / classificationIntent detection, tool selection1–5%
General reasoningStandard Q&A, summarization10–30%
Complex reasoningMulti-step planning, code generation100%

It makes sense when:

  • A significant fraction (>30%) of queries can be handled by cheaper models.
  • The routing decision itself is cheap and reliable.
  • The cost difference between tiers is large (>5×).

It is a mistake when:

  • Nearly all queries require the frontier model — routing overhead is wasted.
  • Routing errors are costly: sending a complex query to a weak model erodes trust more than the cost saved.
  • The codebase complexity of managing multiple models outweighs the savings for a small deployment.
They want nuance, not dogma. Say “I would A/B test quality on the actual query distribution before committing to tiering.”
Mention a concrete strategy: “A small model classifies intent in 50 ms. Billing queries go to a mid-tier model; technical queries with complexity score >0.8 go to the frontier model. I measure quality degradation against the frontier baseline.”

5 Python Concurrency for AI — Async, Semaphores, and Partial Failures

AI engineering interviews drill specific Python patterns: concurrent LLM calls, batch embedding with rate limits, and graceful handling of partial failures. This is not general Python trivia — it is production concurrency.

▶
Why use async instead of threading for concurrent LLM API calls?
Python Concurrency

Both can handle I/O-bound work, but async is the modern default for AI services because it scales to thousands of concurrent connections with one process and makes concurrency points explicit.

DimensionAsync (asyncio)Threading
Memory per concurrent unit~KB (coroutine)~8 MB (thread stack)
Concurrency ceilingThousands–tens of thousandsHundreds
Scheduling overheadEvent loop, cooperativeOS thread scheduler, preemptive
ReadabilityExplicit await at I/O pointsImplicit context switching
Ecosystem fitFastAPI, httpx, asyncpgLegacy sync libraries
 
python · concurrent LLM calls with asyncio.gather
import asyncio

async def call_llm(prompt: str) -> str:
    async with httpx.AsyncClient(timeout=30) as client:
        r = await client.post(LLM_URL, json={"prompt": prompt})
        return r.json()["text"]

async def handle_many(prompts: list[str]) -> list[str]:
    tasks = [call_llm(p) for p in prompts]
    # return_exceptions=False: fail fast on first error
    # return_exceptions=True: collect exceptions as results
    return await asyncio.gather(*tasks)

# 100 prompts × 3s each → ~3s total, not 300s.
They want to hear the memory math: 100 threads × 8 MB = 800 MB of stack alone. Async coroutines are kilobytes each. That is why GenAI platforms prefer asyncio.
Say: “I use async for network I/O — LLM calls, embedding calls, vector DB queries. For CPU-bound work like local reranking, I offload to a thread pool or a separate process, never the event loop.”
▶
Batch-embed 10,000 documents while respecting provider rate limits.
Python Production

Naive asyncio.gather on 10,000 calls will hammer the provider and trigger 429s. Use a semaphore to cap concurrency and a retry policy with exponential backoff. 

python · rate-limited batch embedding
import asyncio
from tenacity import retry, stop_after_attempt, wait_exponential

async def embed_batch_with_limit(docs: list[str], max_concurrent: int = 20):
    sem = asyncio.Semaphore(max_concurrent)

    @retry(
        stop=stop_after_attempt(5),
        wait=wait_exponential(multiplier=1, min=1, max=30),
    )
    async def embed_one(doc: str):
        async with sem:
            async with httpx.AsyncClient() as client:
                r = await client.post(EMBED_URL, json={"input": doc})
                if r.status_code == 429:
                    raise RuntimeError("rate limited")
                r.raise_for_status()
                return r.json()["embedding"]

    tasks = [embed_one(d) for d in docs]
    results = await asyncio.gather(*tasks, return_exceptions=True)

    successes = [r for r in results if not isinstance(r, Exception)]
    failures = [r for r in results if isinstance(r, Exception)]
    print(f"embedded={len(successes)} failed={len(failures)}")
    return successes, failures
A semaphore without retries is still fragile. Provider rate limits are bursty; exponential backoff with jitter is mandatory. Without jitter, all retries fire at the same instant and re-trigger the limit.
They want: semaphore, exponential backoff, jitter, and a distinction between retryable (429, 5xx) and non-retryable (400) errors.
Say: “I size the semaphore to the provider’s concurrency limit — often 10–50 for embedding APIs. I add jitter to the backoff and track the failure rate; if it exceeds 1%, I reduce concurrency automatically.”

How do you handle partial failures in a batch of async LLM calls?
Python

asyncio.gather(..., return_exceptions=True) lets you collect both successes and failures instead of aborting the entire batch. Then you decide the recovery strategy per failure type. 

python · partial failure handling
results = await asyncio.gather(*tasks, return_exceptions=True)

successes, retryable, fatal = [], [], []
for prompt, result in zip(prompts, results):
    if isinstance(result, Exception):
        if isinstance(result, (httpx.TimeoutException, RateLimitError)):
            retryable.append(prompt)
        else:
            fatal.append((prompt, result))
    else:
        successes.append(result)

# Retry only the transient failures, with a smaller concurrency cap
if retryable:
    retried, failed = await embed_batch_with_limit(retryable, max_concurrent=5)
    successes.extend(retried)

# Fatal failures go to a dead-letter queue for human review
await dead_letter_queue.publish(fatal)
The key insight: not all errors are equal. A timeout is retryable; a malformed request is not. Treating them the same wastes money and delays the response.
Say: “I classify errors into retryable and fatal. Retryable failures go back through a backoff-limited queue; fatal failures go to a dead-letter queue with the original prompt and error for triage. The user gets a partial result with a clear failure count, not a silent truncation.”

6 Evaluation & Operations — Metrics, Drift, Observability

Production AI is not “deploy and forget.” You need offline evaluation, online monitoring, and a feedback loop that catches regressions before users do.

▶
How do you monitor a RAG system in production beyond RAGAS?
Monitoring RAG

Offline RAGAS tells you whether a deploy regressed on a golden set. Production monitoring tells you what is happening right now. You need both.

  • Retrieval metrics — top-k hit rate, mean retrieval score, empty-result rate. Alert if hit rate drops more than 5% week-over-week.
  • Generation metrics — token usage, refusal rate, citation coverage, p50/p95 latency.
  • Cache metrics — hit rate by tier, stale-hit rate (cache entries older than TTL still being served).
  • Cost metrics — cost per tenant per day, cost per successful answer.
  • OOD/drift metrics — OOD rate, feature distribution PSI/KS statistics.
They want to hear that you distinguish offline evaluation (golden set) from online monitoring (live traffic). Saying only “we use RAGAS” is incomplete.
Propose a dashboard with four rows: retrieval health, generation health, cost, and safety/OOD. Say: “I alert on rate-of-change, not absolute thresholds, because absolute thresholds drift with traffic mix.”

Implement lightweight data drift monitoring for a tabular model.
Monitoring OOD

Drift monitoring compares incoming feature distributions against training statistics. The simplest production-quality implementation tracks min/max ranges with a margin and computes the OOD rate. 

python · lightweight drift monitor
import logging
from typing import Optional

logger = logging.getLogger(__name__)

class DataDriftMonitor:
    def __init__(self, margin: float = 0.1):
        self.margin = margin
        self.feature_mins: Optional[dict[str, float]] = None
        self.feature_maxs: Optional[dict[str, float]] = None
        self.prediction_count = 0
        self.ood_count = 0

    def fit(self, feature_ranges: dict[str, tuple[float, float]]):
        self.feature_mins = {k: v[0] for k, v in feature_ranges.items()}
        self.feature_maxs = {k: v[1] for k, v in feature_ranges.items()}

    def check(self, features: dict[str, float]) -> dict:
        if self.feature_mins is None:
            return {"in_distribution": True, "warnings": [], "ood_rate": 0.0}

        self.prediction_count += 1
        warnings = []
        for name, value in features.items():
            if name not in self.feature_mins:
                continue
            lo = self.feature_mins[name]
            hi = self.feature_maxs[name]
            range_size = hi - lo if hi > lo else 1.0
            margin = self.margin * range_size
            if value < lo - margin:
                pct = abs(value - lo) / range_size * 100
                warnings.append(f"{name}={value:.4g} is {pct:.1f}% below training min ({lo:.4g})")
            elif value > hi + margin:
                pct = abs(value - hi) / range_size * 100
                warnings.append(f"{name}={value:.4g} is {pct:.1f}% above training max ({hi:.4g})")

        is_ood = len(warnings) > 0
        if is_ood:
            self.ood_count += 1
            logger.warning("OOD input detected: %s", warnings)

        return {
            "in_distribution": not is_ood,
            "warnings": warnings,
            "ood_rate": self.ood_count / self.prediction_count,
        }
Range checks are univariate. They catch obvious outliers but miss correlated anomalies. Pair this with a multivariate method (Mahalanobis, isolation forest) for high-stakes models.
Say: “I fit the monitor on the training set, persist the min/max ranges with the model artifact, and load them at inference time. The OOD rate is emitted as a metric and alerted if it exceeds 2% of traffic.”

7 Behavioral & Scenario Questions

Senior loops include scenario rounds that test debugging judgment and incident response. These are not trivia questions — they are tests of how you think under production pressure.

▶
A RAG endpoint’s p99 latency jumped from 4s to 30s overnight. How do you debug it?
Scenario Debugging

Start by isolating the layer. The latency could be in the API gateway, retrieval, reranking, prompt assembly, or the LLM provider. A trace ID is your best friend.

  1. Check provider status — is the LLM API having an incident? Compare p99 across providers.
  2. Check retrieval latency — vector DB query time, index size, and whether a recent re-index changed the graph structure.
  3. Check reranker — cross-encoders are expensive; a batch size or model change can double latency.
  4. Check connection pooling — exhausted HTTP connection pools to the LLM provider cause queueing that looks like provider latency.
  5. Check traffic mix — a shift toward longer prompts or more complex queries increases token counts and latency.
They want a structured, layer-by-layer approach — not “I would restart the service.” Mentioning trace IDs and connection pools signals real production experience.
Say: “I would first compare the latency breakdown before and after the change. If retrieval is flat and generation latency tripled, I look at provider status and connection pool saturation. If retrieval latency tripled, I check whether a re-index changed the HNSW parameters.”
▶
Your LLM provider goes down completely. Walk me through your incident response.
Incident Resilience

A provider outage is a foreseeable failure, not an emergency. The response should be automated and pre-planned.

  1. Circuit breaker opens — the gateway stops sending requests to the failed provider after N consecutive failures.
  2. Failover chain activates — traffic shifts to the secondary provider (e.g., OpenAI → Anthropic → local vLLM).
  3. Cache-first mode — serve cached responses where possible; for cache misses, return a degraded but honest answer (“I’m having trouble reaching the model; here are relevant sources”).
  4. Rate limiting tightens — protect the secondary provider from the full traffic load; shed low-priority requests.
  5. Alert and communicate — page the on-call, update the status page, and set a review for root cause after recovery.
If you have no secondary provider and no cache, a single provider outage takes down your product. Multi-provider failover is a production requirement, not a nice-to-have.
Frame it as a runbook: “We have a documented failover chain and a circuit breaker that opens automatically. On-call gets paged, and the status page updates within 5 minutes. After recovery, we run a blameless postmortem.”
