# The one mental model that unlocks everything

Every Linux OPPE question is the same question wearing a different costume:
"take structured text in → transform it → produce structured text out."

That's it. That's the whole exam. Once you internalize this, you stop seeing 60 different commands and start seeing one pipeline with interchangeable stages:

read input
→
extract fields
→
transform
→
filter/aggregate
→
format output

Every chapter in this book maps to one stage of that pipeline. cut/awk -F extract fields. tr/sed s/// transform. grep/awk conditions filter. sort/uniq -c aggregate. printf/paste format. Learn the five stages deeply and every "new" question is just a remix.

Pattern recognition is the highest form of intelligence. This entire book is organized around that idea — Chapter 12 explicitly trains you to see the shape of a question before you write a single character of code.

Chapter 01

Bash Foundations

Before you can transform text, you need to control the shell itself: how a script runs, how it remembers values, how it talks to the world through arguments and exit codes. Everything else in this book is built on top of these primitives.

# Scripts & the shebang

Every bash script begins with a shebang line — a comment that isn't really a comment. It tells the OS which interpreter should run the file.

script.sh
#!/bin/bash
# everything below this line is bash code
echo "hello world"

Making it runnable

terminal
chmod +x script.sh    # grant execute permission
./script.sh           # run it (needs +x and shebang)
bash script.sh         # run it without +x — always works
sh script.sh            # run with POSIX sh, not bash — can differ!
source script.sh        # run in the CURRENT shell — variables persist after
In OPPE, if you get "Permission denied" when running ./script.sh, the grader most likely runs your file with bash script.sh directly — but if not, just chmod +x it. Never assume execute permission is already set.

Which shebang to use?

ShebangMeaningWhen OPPE prefers it
#!/bin/bashFull bash feature setDefault answer for any script.sh
#!/bin/shPOSIX sh — no arrays, no [[ ]], no {a..b}Only if the question explicitly says "POSIX sh"
#!/usr/bin/env bashFinds bash in PATH — more portableAccepted equally; safer on macOS
If you're not sure, always write #!/bin/bash for OPPE — the graders expect bash semantics, and features like [[ ]], ${var,,}, and {1..10} are bash-only.

# Variables

Bash variables have zero tolerance for spaces around =. This is the single most common syntax error beginners make.

Wrongnaam = "Rahul"
→ bash tries to RUN a command called "naam"
Rightnaam="Rahul"
→ no spaces, ever
variables.sh
naam="Rahul"
age=20
today=$(date)              # command substitution
files=$(ls | wc -l)       # capture a pipeline's output

echo $naam                     # Rahul
echo "Mera naam ${naam} hai"  # braces disambiguate boundaries
unset naam                    # delete a variable entirely
Use ${var} instead of $var whenever the variable is followed immediately by more text with no separator — e.g. echo "${naam}ji" would break as $naamji without braces (bash would look for a variable literally named naamji).

# Quoting rules — the fine print

Bash has four flavors of quotes/escaping, and choosing the wrong one silently breaks your script on values that contain spaces, $, or globs. This is the second-most-common silent bug after = spacing.

QuoteWhat it doesExample
"double"Expands $variables, $(cmd), ${}, backslashes. Preserves spaces as one argument.echo "hi $USER" → hi root
'single'Literal — nothing is expanded.echo 'hi $USER' → hi $USER
$'ansi'Interprets backslash escapes: \n, \t, \x1b.echo $'a\tb' → tab-separated
\xEscapes the next character.echo "cost: \$5" → cost: $5
WrongFILE="my file.txt"
rm $FILE → tries to rm 'my' and 'file.txt'
RightFILE="my file.txt"
rm "$FILE" → removes 'my file.txt'
Golden rule: quote every variable expansion with double quotes unless you specifically need word-splitting. "$var" almost always, $var almost never. This single habit fixes 80% of "why did my loop break on this file?" bugs.

Command substitution: backticks vs $()

cmd-subst.sh
# old style — avoid
today=`date +%Y`

# new style — always prefer this
today=$(date +%Y)

# $() nests cleanly; backticks do not
count=$(ls $(pwd) | wc -l)   # ← only works with $()

# Arrays — indexed and associative

Bash arrays come in two flavors: indexed (0-based integers, the default) and associative (string keys, like awk arrays). You'll use them any time you want to remember N things while looping.

arrays.sh
# --- indexed array ---
fruits=("apple" "banana" "mango")
echo "${fruits[0]}"       # apple  (first element)
echo "${fruits[-1]}"      # mango  (last element, bash 4.3+)
echo "${#fruits[@]}"      # 3      (number of elements)
echo "${fruits[@]}"       # all elements, as separate words
echo "${!fruits[@]}"      # all indices: 0 1 2
fruits+=("kiwi")         # append

# iterate — always quote "${arr[@]}" to preserve spaces
for f in "${fruits[@]}"; do echo $f; done

# --- associative array (needs declare -A) ---
declare -A count
count[apple]=3
count[banana]=5
for key in "${!count[@]}"; do
    echo "$key -> ${count[$key]}"
done
"${arr[@]}" and "${arr[*]}" are NOT the same thing. [@] expands to one word per element (spaces preserved per element). [*] joins them into a single word using IFS. Use [@] almost always, and always with double quotes.
PYQ pattern When you need to iterate over lines of a file and also need the index (e.g. "print the 3rd student's name"), read into an array first with mapfile -t arr < file, then index directly. mapfile is the fastest, cleanest way to slurp a file into an array — one line of code replaces a while loop.

# Exit status — the silent contract

Every single command that runs in Linux, when it finishes, leaves behind a number between 0 and 255 in $?. This is how scripts communicate success/failure to each other — and OPPE graders check this number more often than you'd think.

ValueMeaning
0Success
1Generic error / "false" from a test
2Shell builtin misuse (often: bad argument)
126Command found but not executable
127Command not found
128+nKilled by signal n (e.g. 130 = Ctrl-C, SIGINT)
1–255Any other failure — meaning varies by command
exit-status.sh
ls /home        # exists → exit code 0
ls /doesnotexist # fails → exit code 2
echo $?          # prints the status of the LAST command only

# setting your own exit code
exit 0   # success
exit 1   # generic failure

# using it in a condition — both forms are equivalent
if [ $? -eq 0 ]; then echo "SUCCESS"; fi
if ./run.sh; then echo "SUCCESS"; fi   # shorter, more common in OPPE answers
Never echo to stdout for an error message. Error text belongs on stderr — always echo "message" >&2. Otherwise your error message pollutes the expected output stream and the grader's diff fails on lines it didn't expect. This single mistake loses many "handle error case" points.
PYQ pattern "Swap file contents" (OPPE-2 Set 2): exact exit codes were graded — 1 for wrong arg count, 2 for missing file, 3 for permission error, 0 + SUCCESS on completion. Read the exit-code table in the question character by character — points are lost purely for using the wrong number.

# Reading input

The single most-used OPPE idiom is reading stdin line by line. You will write this loop dozens of times across an exam.

read-patterns.sh
# from the keyboard / stdin, once
read naam
read -p "Naam batao: " naam   # with a prompt
read -sp "Password: " pass  # silent (no echo) — for passwords
read -t 5 naam              # timeout after 5 seconds
read -n 1 ch                # read exactly 1 character

# THE pattern — line by line from stdin (memorize this)
while read -r line; do
    echo "Got: $line"
done

# from a file instead of stdin
while read -r line; do
    echo "$line"
done < file.txt

# read multiple fields per line
while read -r name age city; do
    echo "$name is $age from $city"
done < people.txt      # splits on IFS (whitespace by default)

# from a command's output (process substitution)
while read -r line; do
    echo "$line"
done < <(ls -la)
Always use -r with read. Without it, backslashes in the input get silently eaten as escape characters — a classic silent-failure bug that costs marks on trailing-backslash test cases.
Reading a file into an array in one line: mapfile -t lines < file.txt. Then ${lines[0]}, ${#lines[@]}, "${lines[@]}" all work. This is faster and often cleaner than a while loop when you need random access.

# Arithmetic — three ways, three purposes

MethodUse whenHandles decimals?
$(( ))Integer math, the default choice❌ no
bcDecimals, square roots, precision✅ yes
exprLegacy / POSIX sh scripts❌ no
awkYou're already in awk, or need float math in a pipeline✅ yes
arithmetic.sh
a=10; b=3

echo $((a + b))    # 13
echo $((a - b))    # 7
echo $((a * b))    # 30
echo $((a / b))    # 3   ← integer division, truncates!
echo $((a % b))    # 1   ← remainder
echo $((a ** b))   # 1000 ← power

((a++))          # a = a + 1, in-place
((a += 5))       # a = a + 5

# decimals need bc
echo "scale=2; 10/3" | bc   # 3.33
echo "sqrt(16)" | bc         # 4

# awk prints floats natively
awk 'BEGIN{ printf "%.4f\n", 10/3 }'   # 3.3333
PYQ pattern Summing a column of numbers piped in one per line? paste -sd'+' file | bc turns 1\n2\n3\n4 into the expression 1+2+3+4 and evaluates it — one of the most reused one-liners across every OPPE paper.
$((10 / 3)) gives 3, not 3.33. If you need a decimal average in pure bash, either pipe through bc (echo "scale=2; $sum / $count" | bc) or route the calculation through awk — bash arithmetic is strictly integer.

# set -euo pipefail — the prologue

Almost every serious bash script begins with this trio. Each flag changes bash's failure behaviour to be stricter, so bugs surface immediately instead of silently.

FlagMeaningEffect
-eExit on errorScript quits the moment any command returns non-zero
-uUnset variable errorUsing $undefined is a fatal error, not empty
-o pipefailPipe failure detectionA pipe fails if any stage fails, not just the last
strict-mode.sh
#!/bin/bash
set -euo pipefail

# now a failing command aborts the script
cp missing.txt dest/       # script exits here
echo "this line never runs"
When NOT to use set -e: if a question explicitly requires you to try a command that might fail and then handle the failure yourself (if ! cp ...; then ...), strict mode will kill your script before your handler runs. Also, grep returns 1 when no match — under set -e, that aborts your script. Use grep ... || true or wrap in if.

# Subshells & sourcing

This is one of the most confusing bash behaviours for beginners, and it silently eats variable assignments if you're not aware of it.

SyntaxWhat runs whereVariable persistence
bash script.shNew shell processNone — script's vars die with it
source script.sh / . script.shCurrent shellPersist after script returns
( commands )SubshellDiscarded when subshell exits
{ commands; }Current shellPersist
cmd | while readwhile runs in subshellDiscarded after loop
while read < <(cmd)Current shellPersist after loop
Wrong — count stays 0count=0
echo "a b c" | while read -r w; do
  count=$((count+1))
done
echo $count # 0
Right — count is 3count=0
while read -r w; do
  count=$((count+1))
done < <(echo "a b c")
echo $count # 3
Remember this one rule: piping into a loop (cmd | while ...) runs the loop in a subshell, and any variable you set inside is thrown away when the loop ends. Use process substitution (< <(cmd)) or a redirected file (< file) instead whenever you need the loop to leave data behind.

Logical combinators

logic.sh
[ cond1 ] && [ cond2 ]   # AND — both true
[ cond1 ] || [ cond2 ]   # OR — either true
[ ! condition ]          # NOT

# [[ ]] is the modern, safer, recommended form
[[ $a -eq $b && $c -eq $d ]]
[[ $str == "hello" || $str == "world" ]]
[[ $str =~ ^[0-9]+$ ]]   # regex match — only works inside [[ ]]
[[ -f $file && -r $file && -s $file ]]   # 3-way AND
Prefer [[ ]] over [ ] when you can — it doesn't word-split unquoted variables, supports &&/|| directly inside it, and supports regex matching with =~. [ ] is the POSIX-portable choice; [[ ]] is the bash-safe choice. OPPE accepts both — use [[ ]] unless told otherwise.

# For loops — five flavors

for-loops.sh
# 1. literal list
for i in 1 2 3 4 5; do echo $i; done

# 2. brace range (with optional step)
for i in {1..10}; do echo $i; done
for i in {0..20..5}; do echo $i; done   # 0,5,10,15,20
for c in {a..e}; do echo $c; done       # a b c d e

# 3. C-style (best when you need custom step logic)
for ((i=0; i<5; i++)); do echo $i; done
for ((i=10; i>0; i-=2)); do echo $i; done   # 10 8 6 4 2

# 4. glob over files
for file in *.txt; do echo "Processing: $file"; done

# 5. over an array
fruits=("apple" "banana" "mango")
for fruit in "${fruits[@]}"; do echo $fruit; done

# 6. over a command's output
for user in $(cut -d: -f1 /etc/passwd); do echo $user; done

# 7. positional arguments
for arg in "$@"; do echo "arg: $arg"; done
Looping over a command's raw output with for x in $(cmd) word-splits on whitespace — if lines have spaces in them, they will silently be torn apart. Use while read -r line instead whenever lines might contain spaces.

# Until loops

until is the mirror of while — it loops as long as the condition is false, and stops when it becomes true. Rarely used, but you should recognize it if it appears.

i=1
until [ $i -gt 5 ]; do

done

Chapter 03

Functions

Bash functions don't "return" values the way Python or C do — they echo output and set an exit status. Understanding this distinction is the difference between fighting bash and flowing with it.

# Defining and calling

functions.sh
# three valid definition syntaxes — all equivalent
greet() { echo "Hello $1!"; }
function greet { echo "Hello $1!"; }
function greet() { echo "Hello $1!"; }

greet "Rahul"            # Hello Rahul!

# functions can access their OWN args separately from script args
describe() {
    echo "function received $# args: $@"
}
describe a b c
# function received 3 args: a b c
Inside a function, $1, $2, $# etc. refer to the function's own arguments, not the script's. They shadow the outer values for the duration of the call.

# "Returning" a value

Bash functions have two separate output channels — use the right one for the right purpose:

ChannelHowUse for
Dataecho + capture with $(func)Returning a computed value (string/number)
Statusreturn N (0–255) → read via $?Signalling success/failure only
return-vs-echo.sh
get_square() {
    echo $(($1 * $1))     # DATA channel — this is the "return value"
}
result=$(get_square 5)
echo $result             # 25

check_file() {
    if [ -f "$1" ]; then
        return 0          # STATUS channel — success
    else
        return 1          # STATUS channel — failure
    fi
}
if check_file "test.txt"; then
    echo "File exists!"
fi
return can only carry a number 0–255 — it is not for sending back computed data. A common beginner mistake is trying return $result where result is a string or a number outside that range — it silently truncates/breaks. Always echo data, return only status.
Capturing multiple values from a function: either print them one per line and read into an array with mapfile, or use an out variable by name (via declare -n, see the "Returning arrays" section below). OPPE-style questions rarely need this — usually one line of output per call is enough.

# Recursion

Bash functions can call themselves. Useful for factorials, tree walks, and any place where the natural solution is "do it for the smaller case, then combine."

recursion.sh
factorial() {
    if [ $1 -le 1 ]; then
        echo 1
        return
    fi
    sub=$(factorial $(($1 - 1)))   # recursive call — capture via $()
    echo $(($1 * sub))
}
echo "5! = $(factorial 5)"   # 5! = 120

countdown() {
    if [ $1 -lt 0 ]; then return; fi
    echo $1
    countdown $(($1 - 1))
}
countdown 3   # 3 2 1 0
Bash has no tail-call optimization and a fairly shallow default recursion depth. Don't recurse thousands of levels deep in a bash script — it will either be slow or hit a stack limit. For OPPE-scale inputs (dozens to hundreds of items), recursion is fine.

# Returning arrays (via nameref)

You can't echo an array and capture it back — the elements get word-split apart. The clean solution is a nameref: pass the name of the caller's array in as an argument, and modify it by reference.

return-array.sh
get_odds() {
    local -n out=$1     # -n makes 'out' a reference to the caller's variable
    out=()
    for ((i=1; i<=$2; i+=2)); do
        out+=($i)
    done
}

evens=(2 4 6 8 10)
get_odds odds 10
echo "${odds[@]}"       # 1 3 5 7 9

# Function libraries & sourcing

If an OPPE question asks for helper functions in a separate file, put them in lib.sh and source them into the main script.

# PCRE mode (grep -P)

When a pattern uses \d, lookahead, or lookbehind, you need -P. It's slower than -E, so only reach for it when the pattern requires it.

# lookahead — "match X only if followed by Y"
grep -P "foo(?=bar)" file.txt              # matches 'foo' in 'foobar' but not 'foobaz'

sed reads input one line at a time, applies your commands to that line, and prints the result — then moves to the next line. This single mental model explains every sed behaviour you'll ever see.

# The seven core commands

s — substitute
sed 's/old/new/g' file

sed '/pattern/d' file

Explicitly print matching lines. Almost always paired with -n so you don't get doubled output.

Insert a new line after the matched line. GNU sed accepts a text without a backslash.
i — insert
sed '1i\##HEADER##' file
Insert a new line before the matched line. 1i prepends to the very top of the file.
c — change
sed '/pattern/c\replacement' file
Replace the entire matched line with new text — different from s/// which only replaces the matched substring.
y — transliterate
sed 'y/abc/ABC/' file
Character-by-character replace, like tr. a→A, b→B, c→C. No regex — literal chars only. Lengths must match exactly.
= — print line number
sed -n '/pattern/=' file
Print the line number of each matching line — useful for locating matches.
q — quit early
sed '10q' file
Stop processing after line 10 (or after the first match if combined with a pattern).

# Capture groups — swap, reorder, restructure

This is the single most powerful sed feature and the source of nearly every "hard" sed question in OPPE. Wrap parts of your pattern in () (with -E) or \(\) (default BRE), then reference them in the replacement as \1, \2, etc.

Command
echo "2023-03-15" | sed -E \
  's/([0-9]{4})-([0-9]{2})-([0-9]{2})/\3-\2-\1/'
Output
15-03-2023

Group 1 = year, group 2 = month, group 3 = day. The replacement string just reorders them: \3-\2-\1.

Swap first two colon fields
echo "root:x:0" | sed -E \
  's/^([^:]*):([^:]*)/\2:\1/'
Output
x:root:0
Reorder lastname, firstname → firstname lastname
echo "Sharma, Raj" | sed -E \
  's/^([^,]+), *(.+)$/\2 \1/'
Output
Raj Sharma
& in a replacement means "the whole match" — sed 's/hello/[&]/' turns hello into [hello] without needing to retype the match. Combine with \U / \L for case changes on the whole match.

# Multiline operations — N, D, P

By default sed handles one line at a time. To reach across line boundaries, use N (append next line) or z (in GNU, replace pattern with NULs). These three commands are the standard tools for paragraph-level work.

CommandEffect
Nread the next line into the pattern space (so it now contains two lines separated by \n)
Ddelete up to the first \n in the pattern space, then restart the cycle (doesn't read a new line)

multiline.sh
# join every paragraph (blocks of non-blank lines) into one line
sed '/./{H;$!d};${x;s/\n/ /g;p}' file

# In-place editing (-i)

By default sed writes to stdout and leaves the file untouched. With -i, sed modifies the file in place — no redirect needed.

# use a custom backup suffix (with a space before it)

# PYQ — Full Log Processor hard appeared 3× across papers

This exact shape — filter by level, lowercase the level, swap the timestamp — has shown up in the May 2025 PYQ, OPPE-2 Set 1, and the OPPE-2 practice paper. Learn this once, solve it forever.

[ERROR] (2023-03-15 12:03:00) err msg

# PYQ — Redact PAN numbers med

PAN format: 3 letters + 1 letter from a fixed set + 1 letter + 4 digits + 1 letter (all uppercase, no lowercase mixing).

script.sed
s/\b[A-Z]{3}[CPHFATBLJG][A-Z][[:digit:]]{4}[A-Z]\b/##HIDDENPAN##/g

Common sed mistakes hall of fame:
  • Forgetting -E then using +/?/| unescaped — they become literal characters in default BRE mode.
  • Using \( \) for groups with -E — in ERE mode groups are just ( ), no backslash.
  • Forgetting the trailing g on s/// and only the first match on each line gets replaced.
  • Using sed 's/.../.../' when a whole-line replacement was wanted — need c\ instead.
  • Forgetting -n with p — every line gets printed twice.
  • Using -i and then reading the file — it's already modified; you can't undo.

If sed is a text editor, awk is a tiny programming language that thinks in rows and columns. Every awk program is a series of pattern { action } pairs — "when this is true, do this."

structure

# getline & nextfile

getline reads the next line manually — useful when you need to look ahead or read from a different source.

getline.sh
# read the next line of the current input

# Processing two files (join-style)

102 gadget
101 grommet

    for (i=1; i<=NF; i++) { row_sum += $i; col[i] += $i }
    print $0, row_sum/NF       # row average
    rows++                     # count how many rows we saw, for the END block
}
END {
    for (i=1; i<=NF; i++)
        printf "%s%s", col[i]/rows, (i<NF ? "," : "\n")
}

Pipes & I/O Redirection

The plumbing that connects every command in this book to every other command. Understanding streams is what turns a list of isolated tools into one flexible instrument.

# Pipes — the | operator

| takes the stdout of the command on its left and feeds it as stdin to the command on its right. Chain as many as you like.

pipe-chain.sh
cat file | tr ' ' '\n' | sort | uniq -c | sort -nr | head -10

Read this left to right as a sentence: "take the file, split into words, sort them, count duplicates, sort by count descending, keep the top 10." Every OPPE pipeline is readable this way once you're fluent.

Every stage of a pipe runs in parallel. This means yes | head -1 exits quickly — head reads one line, then closes its stdin, which sends SIGPIPE to yes. You don't need to worry about this in OPPE, but it's why some pipelines finish instantly on infinite input.

# Named pipes (FIFO)

A named pipe looks like a file but behaves like a pipe. Two processes can communicate through it by name — rarely needed in OPPE, but worth recognizing.

# exec & FD juggling

exec is how you permanently reassign file descriptors for the rest of the script. Used for: opening a file once, writing to it many times, and redirecting everything that follows.

exec.sh
# open FD 3 for writing, redirect all stdout from now on
exec 3>logfile.txt
echo "this goes to logfile" >&3
echo "this also goes to logfile" >&3
exec 3>&-              # close FD 3

# redirect the WHOLE SCRIPT's stdout to a file
exec > output.txt
echo "all stdout from here goes to output.txt"

# swap stdout and stderr for the rest of the script
exec 3>&1 1>&2 2>&3 3>&-
exec > file truncates the file at the moment it runs. If you use it inside a function or script and forget, everything before that point has already gone to the original stdout. This is usually the wrong tool for an OPPE question — prefer a per-command > file redirect.

# Here-strings & process substitution

advanced-io.sh

# process substitution: treat a COMMAND'S OUTPUT as if it were a file

# PCRE lookarounds — advanced matching

Available only via grep -P (and inside perl/pcre2 tools). Lookarounds let you assert context without consuming it in the match.

SyntaxMeaning

(?!...)negative lookahead — match X only if NOT followed by ...

# Greedy vs lazy matching

By default, * and + are greedy — they match as much as possible. In PCRE you can add a ? to make them lazy — match as little as possible.

Input
a1=5, a2=10, a3=20
Different matches
greedy:  "1=5, a2=10, a3=2"
lazy:    "1=5"
greedy pattern: .+[0-9]
lazy pattern:   .+?[0-9]
greedy-vs-lazy.sh
# greedy — matches everything between the FIRST < and LAST >
grep -oP "<.+>" file

# lazy — matches each individual tag
grep -oP "<.+?>" file

# extract each quoted field lazily
grep -oP '"[^"]*"' file         # character class alternative to lazy
In BRE/ERE there's no lazy quantifier. The usual substitute is a negated character class: [^>]* instead of .+? — "anything that isn't >". This gets you lazy-like behaviour in sed and grep -E.

# Catastrophic backtracking

Nested quantifiers like (a+)+ or (.*)* can cause exponential backtracking on long non-matching input. The regex engine tries every possible split of the input — and quickly spirals into millions of attempts.

Can hang on long input(a+)+b
Safe rewritea+b
Never write (.*)*, (.+)+, or any pattern where a quantifier wraps another quantifier over the same characters. If an OPPE regex seems to hang, this is why. Rewrite using a specific character class — [^,]+ instead of (.+)+ — to give the engine a single, unambiguous way to match.

Where even toppers lose points — generalization gaps

# trap — cleanup on exit

trap registers a command to run when the shell receives a signal or exits. Use it to guarantee cleanup of temp files even when the script is interrupted.

trap.sh
#!/bin/bash
tmp=$(mktemp)

# run cleanup on EXIT, INT (Ctrl-C), TERM (kill)
trap 'rm -f "$tmp"; echo "cleaned up" >&2' EXIT INT TERM

echo "working with $tmp"
# ... even if we get Ctrl-C, tmp is removed

# ignore Ctrl-C temporarily
trap '' INT
# restore default afterwards
trap - INT
trap ... EXIT runs on every exit — normal, exit N, or a signal. This makes it the perfect place for "cleanup the temp files I created." A script that uses mktemp without a trap will leave orphan temp files behind on Ctrl-C.

# Performance notes

OPPE inputs are small — usually under a few thousand lines. You almost never need to worry about speed. But two patterns are worth avoiding on principle:

  • Don't spawn a subprocess inside a tight loop. for i in {1..10000}; do echo $i | sed 's/x/y/'; done forks 10,000 processes. Do the whole transform outside the loop, or use a single awk that does it all.
  • Don't read a file with cat | while read. Use while read < file — the latter avoids a useless cat process and a pipe.
The fastest solution in an OPPE is almost always one awk program instead of a bash for-loop that shells out repeatedly. If your solution has three or more $(...) calls inside a loop, ask whether awk could do the whole thing in one pass.

The seven mistakes that cost the most marks, ranked:
  1. Missing g flag on sed s/// (only replaces first match per line)
  2. Using default BRE regex features (+ ? |) without -E
  3. Running uniq on unsorted input
  4. Piping into tr with a filename argument instead of < redirect
  5. Spaces around = in variable assignment
  6. Error messages going to stdout instead of stderr (>&2)
  7. Assuming NR==1 when the question actually needs FNR==1 per file
